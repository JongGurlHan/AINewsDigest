# Architecture Decision Records

## 철학
MVP 속도 최우선. 다만 **매일 아침 자동으로 돌아가야 하는 서비스**이므로, 사람이 개입해야만 복구되는 구조는 만들지 않는다. 외부 의존성은 인터페이스 뒤에 두어 테스트 가능하게 하되, 추상화 자체를 목적으로 삼지 않는다. 작동하는 최소 구현을 선택한다.

---

### ADR-001: 실행 환경으로 Oracle Cloud Always Free 선택
**결정**: ARM64 Always Free VM 한 대에 Spring Boot + PostgreSQL을 Docker Compose로 올린다.
**이유**: 운영 예산 상한이 월 5,000원이다. 유료 PaaS는 최소 $5(약 7,000원)부터라 초과한다. Always Free는 인프라 비용이 0원이라 예산 전액을 LLM 호출에 쓸 수 있고, 공인 IP가 있어 랜딩페이지 공개도 가능하다.
**트레이드오프**: 계정 생성에 해외결제 카드 인증이 필요하고 리전에 따라 ARM 인스턴스 재고가 없을 수 있다. ARM64라서 x86 러너(GitHub Actions)에서 만든 이미지를 그대로 쓸 수 없다.

### ADR-002: LLM은 Codex CLI가 아닌 OpenAI API 직접 호출
**결정**: Spring의 `RestClient`로 OpenAI Chat Completions를 호출한다. mini급 모델을 쓰고 structured output으로 JSON 응답을 강제한다.
**이유**: Codex는 코딩 에이전트 제품이지 요약·번역용 모델이 아니다. 서버에서 CLI를 셸 아웃하면 헤드리스 환경의 토큰 만료 재인증, 자유 형식 출력 파싱, 수십 초~수 분의 실행 시간이 전부 새벽 배치의 실패 지점이 된다. API 직접 호출은 타임아웃·재시도·토큰 사용량을 코드로 제어할 수 있고 MockWebServer/WireMock으로 테스트된다.
**트레이드오프**: 종량 과금이 발생한다(예상 월 약 600원). 구독제 정액이 아니라 사용량이 튀면 비용도 튄다.

### ADR-003: 구독은 텔레그램 딥링크 직결 방식
**결정**: 랜딩의 구독 버튼을 `https://t.me/<bot>?start=web`으로 연결하고, 봇이 `/start`를 받은 시점에 `chat_id`를 저장한다.
**이유**: 텔레그램 봇은 상대가 먼저 말을 걸기 전에는 메시지를 보낼 수 없다. 발송에 필요한 `chat_id`는 `/start` 순간에만 얻을 수 있으므로 "웹에서 주소를 입력받아 발송" 모델이 원천적으로 불가능하다. 딥링크는 이메일·이름을 받지 않아 개인정보 보관 책임이 0이고, start payload로 유입 경로도 구분할 수 있다.
**트레이드오프**: 웹 폼이 없어 랜딩페이지의 웹 계층이 얇아진다. 이를 아카이브 페이지로 보완한다(ADR-004).

### ADR-004: 랜딩 + 아카이브 웹 화면을 만든다
**결정**: `/`(랜딩, 최신호 노출), `/archive`(날짜별 목록), `/archive/{date}`(상세) 3페이지를 Thymeleaf로 만든다.
**이유**: 구독이 딥링크 한 번으로 끝나면 JPA로 조회하는 화면이 하나도 남지 않는다. 발송 내용을 어차피 DB에 쌓으므로 조회 화면은 거의 공짜로 얻어진다. 방문자는 설명 대신 실물을 보고 구독을 판단하고, 채용담당자는 날짜가 쌓인 걸 보고 서비스가 실제로 매일 돌고 있음을 확인한다.
**트레이드오프**: 페이지 3개와 템플릿 유지 비용이 늘어난다.

### ADR-005: 수집은 Hacker News 중심 + 공식 피드 소수
**결정**: HN Algolia API(키 불필요, points·날짜 필터 지원)를 물량의 축으로 삼고, OpenAI News RSS · Claude Code CHANGELOG · Cursor changelog · Simon Willison Atom을 보조로 붙인다.
**이유**: HN은 "개발자가 실제로 반응한 것"만 상위로 올라오므로 이 서비스의 목표와 정확히 맞는다. Anthropic은 RSS를 제공하지 않는데(`/rss.xml`, `/news/rss.xml` 모두 404), Anthropic 발표는 거의 항상 HN 상단에 올라오므로 HN이 이 구멍을 메운다. 소스가 5개 안팎이라 어댑터 구현량도 감당 가능하다.
**트레이드오프**: HN은 영어권·미국 편향이고 낚시성 글이 섞인다. 테크미디어 카테고리 피드는 정확도가 낮아(AI 카테고리에 SpaceX 기사가 섞임) MVP에서 제외했다.

### ADR-006: 본문은 jsoup으로 직접 추출한다
**결정**: 선별된 기사만 원문을 받아 jsoup으로 `article`/`main`/`p` 휴리스틱 추출 후 앞 3,000자를 사용한다. 타임아웃 5초, 실패 시 해당 기사를 후보에서 탈락시킨다.
**이유**: HN Algolia는 `title`, `url`, `points`만 주고 외부 링크 기사의 본문을 주지 않는다. 제목만으로 "3~4문장 한글 요약"을 시키면 모델이 내용을 지어내고, 그 환각이 매일 아침 확신에 찬 문장으로 발송된다. 뉴스 서비스에서 이는 치명적이다. jsoup은 의존성 하나뿐이고 HTML 프래그먼트를 픽스처로 고정하면 네트워크 없이 단위 테스트가 가능하다.
**트레이드오프**: 페이월·봇 차단 사이트는 실패한다. 이를 감안해 필요 건수보다 넉넉히(8건) 선별한 뒤 크롤링한다.

### ADR-007: 선별과 요약을 2단계 LLM 호출로 분리
**결정**: 1차 호출은 제목·출처·points만으로 채점해 상위 8건을 고르고, 그 8건만 크롤링한 뒤 2차 호출로 요약한다.
**이유**: 크롤링은 파이프라인에서 가장 느리고 가장 잘 깨지는 구간이다. 선별을 먼저 하면 크롤링 횟수가 절반 이하로 줄어 실패·차단 노출이 감소한다. 선별기와 요약기를 각각 독립적으로 테스트할 수 있어 TDD에도 맞는다.
**트레이드오프**: 호출이 2회로 늘고, 선별을 제목만 보고 하므로 판단 정확도가 다소 떨어진다.

### ADR-008: 텔레그램 업데이트는 웹훅이 아닌 롱폴링으로 수신
**결정**: 앱 기동 시 백그라운드에서 `getUpdates`를 롱폴링한다.
**이유**: 웹훅은 신뢰된 CA 인증서를 갖춘 공개 HTTPS(443/80/88/8443)를 요구하고 로컬 테스트에 터널이 필요하다. 롱폴링은 서버에서 나가는 연결이라 도메인·인증서·인바운드 방화벽 설정이 전부 불필요하고, 로컬 개발 환경이 운영과 동일하게 동작한다. 앱이 내려간 동안의 `/start`도 텔레그램이 24시간 보관하므로 재기동 시 따라잡는다.
**트레이드오프**: 연결을 상시 유지해야 하고 웹훅보다 반응이 약간 느리다.

### ADR-009: 메시지는 HTML parse_mode, URL은 도메인 하이퍼링크
**결정**: `parse_mode=HTML`을 쓰고 `disable_web_page_preview=true`를 켠다. 출처는 `<a href="…">cursor.com</a>` 형태로 도메인만 노출한다.
**이유**: MarkdownV2는 `_ * [ ] ( ) ~ > # + - = | { } . !`를 전부 이스케이프해야 하고 하나라도 빠지면 발송 전체가 400으로 실패한다. LLM이 만든 한글 요약에는 마침표가 반드시 들어가므로 매일 터질 구조다. HTML은 이스케이프 대상이 `& < >` 셋뿐이다. 또한 텔레그램의 4,096자 제한은 "after entities parsing" 기준이라 하이퍼링크의 URL은 글자수에 포함되지 않는다. 도메인만 노출하면 글자수를 아끼면서 출처 신뢰도 판단도 가능하다.
**트레이드오프**: 원문 URL 전체가 화면에 보이지 않아 복사해 옮기기는 불편하다.

### ADR-010: 장애 감지는 관리자 알림 + 데드맨스위치 병행
**결정**: 배치 실패 시 관리자 `chat_id`로 알리고, 동시에 발송 성공 시 healthchecks.io에 핑을 보낸다. 정해진 시각까지 핑이 없으면 외부에서 알림이 온다.
**이유**: 실패 알림만으로는 "앱이 죽어서 알림조차 못 보내는" 상황을 잡지 못한다. 이 서비스는 "오늘의 AI 뉴스는 없습니다"를 정상 동작으로 설계했기 때문에 침묵과 장애가 구분되지 않는다. 성공 시 핑을 보내는 역방향 감시가 있어야 이 사각지대가 사라진다. 둘 다 0원이고 구현은 HTTP GET 한 줄이다.
**트레이드오프**: 외부 서비스 의존이 하나 늘어난다(단, 죽어도 발송 자체에는 영향이 없다).

### ADR-011: 테스트 DB는 H2가 아닌 Testcontainers PostgreSQL
**결정**: H2를 제거하고 테스트도 실제 PostgreSQL 컨테이너에서 실행한다. 테스트에서 Flyway를 활성화하고 `ddl-auto: validate`를 쓴다.
**이유**: 기존 설정은 테스트가 `create-drop` + Flyway 비활성이라 **마이그레이션이 한 번도 실행되지 않은 채 전부 통과**했다. 마이그레이션에 오타가 있어도 배포 시점 `validate`에서야 앱이 뜨지 않고, 그게 새벽이면 아침 발송이 통째로 날아간다. H2의 `MODE=PostgreSQL`은 완전 호환이 아니어서 H2 통과가 PostgreSQL 통과를 보장하지도 않는다.
**트레이드오프**: 개발 중 Docker가 떠 있어야 하고 테스트 시작이 몇 초 느려진다. 테이블 4개 규모라 손해는 작다.

### ADR-012: 패키지는 5개 도메인 계층형 (헥사고날 아님)
**결정**: `subscription` / `digest` / `collect` / `curation` / `delivery` + `global`. 아웃바운드 5개만 인터페이스 뒤에 둔다.
**이유**: 이 앱은 로직이 얇고 I/O가 두껍다. 선별·요약은 LLM이, 본문 추출은 jsoup이, 발송은 텔레그램이 한다. 순수 도메인 로직은 URL 정규화, 중복 배제, 글자수 초과 시 건수 축소, 구독 상태 전이 정도다. 격리해서 지킬 도메인 모델이 얇은데 격리 구조만 두껍게 만들 이유가 없다. 헥사고날의 테스트 이점 대부분은 "외부 의존을 인터페이스로 감싼다"에서 오고 그건 계층형에서도 얻어진다.
**트레이드오프**: 포트-어댑터 대비 구조적 강제력이 약해 규율에 의존한다. 테이블 4개짜리 MVP에서는 이 정도가 적정하다고 판단했다.

### ADR-013: "보낼 뉴스 없음"은 LLM 점수 임계값으로 판정
**결정**: 1차 선별에서 각 후보에 1~5점을 매기고 3점 이상만 채택한다. 3점 이상이 0건이면 `오늘의 AI 뉴스는 없습니다.`를 보낸다.
**이유**: HN과 RSS를 긁으면 후보가 0건인 날은 사실상 오지 않으므로, "뉴스 없음"은 수집 실패가 아니라 품질 판단의 결과여야 한다. 기준이 없으면 모델이 매일 억지로 5건을 채우고 "엄선"이 무의미해진다. 점수를 DB에 남겨두면 프롬프트를 건드리지 않고 임계값만 조정해 발송 빈도를 튜닝할 수 있다.
**트레이드오프**: 임계값이 높으면 "뉴스 없음"이 잦아 구독 가치가 떨어진다. 운영하며 조정이 필요하다

### ADR-014: 발송 여부는 `sent_at`으로 판정하고, 발송은 at-least-once로 보장한다
**결정**: `digest.status`는 콘텐츠 성격(PENDING/SENT/EMPTY)만 나타내고 발송 여부는 `sent_at`으로 판정한다. EMPTY 다이제스트는 발송 후에도 status를 EMPTY로 유지한 채 `sent_at`만 채운다. 발송 재개는 해당 다이제스트에 이미 SUCCESS 로그가 있는 구독자를 건너뛰는 방식으로 처리한다.
**이유**: ADR-013에 따라 "뉴스 없음"은 정상 동작이므로 EMPTY로 나간 날이 기록에 남아야 임계값을 튜닝할 수 있는데, 발송 후 EMPTY를 SENT로 덮으면 그 정보가 사라진다. 그렇다고 EMPTY를 발송 대상에서 빼면 PRD의 "침묵하지 않는다"가 깨진다. 두 축을 분리하면 발송·아카이브 노출·멱등성 판정이 전부 `sent_at` 하나로 통일된다. 또한 구독자 순회 도중 프로세스가 죽으면 다이제스트는 여전히 미발송 상태라 재실행 시 처음부터 다시 보내게 되는데, 성공 로그 기준 스킵이 이를 막는다. `sent_at` 컬럼이 이미 있어 스키마 변경이 없다.
**트레이드오프**: 상태 판정 기준이 컬럼 두 개로 나뉘어 조회 조건을 매번 정확히 써야 한다. 텔레그램 호출과 로그 커밋 사이에 죽은 1건은 여전히 중복될 수 있어 exactly-once는 포기한다. `delivery_log`에 DB 레벨 유일 제약을 두지 않았다 — 재시도 실패 로그가 (digest, subscriber)당 여러 건 쌓이는 설계라 평범한 UNIQUE는 정상 흐름을 깨뜨린다..

### ADR-015: HTTP 클라이언트는 `starter-restclient` + 어댑터별 타임아웃
**결정**: `spring-boot-starter-restclient`를 명시적으로 추가하고, 타임아웃은 전역 프로퍼티가 아니라 각 어댑터 생성자에서 `HttpClientSettings.withReadTimeout()`으로 지정한다.
**이유**: Boot 4에서 스타터가 잘게 쪼개지면서 `spring-boot-starter-webmvc`의 의존성이 `starter`·`starter-jackson`·`starter-tomcat`·`http-converter`·`webmvc` 다섯 개로 줄었다. `RestClient.Builder`를 만드는 `spring-boot-restclient`도, `spring.http.client.*`를 정의하는 `spring-boot-http-client`도 여기 포함되지 않는다. Boot 3 감각으로 "웹 스타터를 넣었으니 RestClient가 있겠지" 하면 기동 시점에 `NoSuchBeanDefinitionException`이 나고, 설정에 적어둔 타임아웃 프로퍼티는 아무도 읽지 않는 죽은 키가 된다. 타임아웃을 어댑터별로 두는 이유는 요구 시간이 6배 차이나기 때문이다 — 롱폴링은 30초 이상 기다려야 정상이고 LLM 요약은 60초가 필요한데 수집은 10초 안에 포기해야 한다. 전역값을 하나 고르면 셋 중 둘이 깨진다.
**트레이드오프**: 어댑터마다 3~4줄의 빌더 구성 코드가 반복된다. 공용 팩토리로 묶으면 그 대가로 타임아웃 차이가 설정 밖으로 숨는다.

### ADR-016: 아웃바운드 포트의 실패는 예외가 아니라 반환 타입으로 표현한다
**결정**: `NewsSource.fetch`는 `FetchResult(articles, failed)`, `UpdateSource.getUpdates`는 `PollResult`(sealed), `Messenger.send`는 `SendResult`(sealed), `ArticleContentExtractor.extract`는 `Optional`을 돌려준다. 반대로 `ArticleSelector`·`ArticleSummarizer`의 실패는 예외로 전파한다. **빈 컬렉션으로 실패를 표현하지 않는다.**
**이유**: 이 파이프라인에서 부분 실패는 예외 상황이 아니라 매일 일어나는 정상 흐름이다(페이월 사이트, 죽은 피드, 봇을 차단한 구독자). 예외로 표현하면 호출자가 매번 try-catch로 흐름을 복원해야 하고, 발송 루프에서는 한 명의 실패가 나머지 구독자를 통째로 날린다. 그렇다고 빈 리스트로 뭉개면 더 나쁘다 — "결과가 없음"과 "실패해서 없음"이 같은 값이 되어 **장애가 정상 동작으로 위장된다.** 실제로 그 구멍이 두 군데 있었다. 수집 소스 3개가 전부 죽어도 후보 0건이라 EMPTY가 정상 발송되고 헬스체크 핑까지 나가 ADR-010의 감시가 무력화됐고, 롱폴링은 실패와 "업데이트 없음"이 둘 다 빈 리스트라 폴러가 백오프를 걸 방법이 없었다. 선별·요약만 예외인 것은 그 실패가 부분 실패가 아니기 때문이다 — 요약이 없으면 그날 다이제스트 자체가 성립하지 않으므로 스케줄러까지 올려보내 재시도·알림을 결정하게 한다.
**트레이드오프**: 포트 하나당 결과 타입이 하나씩 늘어 클래스 수가 는다. 호출부는 성공 분기만 쓰고 실패 필드를 조용히 무시할 수 있어, 결과 타입을 쓴다는 사실만으로 처리가 보장되지는 않는다.
